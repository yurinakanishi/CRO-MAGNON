# 起動時のワールド計算をビルド時へ移す（world data bake、2026-10-11）

ユーザー指定「スマホとかでも快適にゲームができるように容量とかパフォーマンス改善したい。小手先のてくにっくではなく、根本から。」の続き（[配信用変換](delivery-cooking-2026-10-11.md) の「残る根本課題3：起動JavaScript」）。ユーザーの選択「性能改善の根本課題の残りも進める（見た目を変えずに）」による。

## 原因：毎回の読み込みで、同じワールド生成をやり直していた

起動JS（6.91MB、gzip約1.16MB）の85%は5つのデータモジュール（海岸2.63MB・山の地表2.03MB・城の地表0.75MB・ランドマーク0.29MB・洞窟0.20MB）だった。さらに読み込み時に、決まった入力から決まった結果を出す計算を毎回していた。Node（このPC、CPU制限なし）で測った `collision`・`terrain`・`world` の読み込みは約600msで、内訳は次のとおり。

| 項目 | 時間 | 内容 |
| --- | --- | --- |
| 海岸の格子の展開と補正 | 232ms | 47万個のランを地球の格子（2048×1024）に展開し、ワールドの格子（4096×2048）へ写し、旧い湾（約12万セル）と山すそ（約2万セル）を距離計算で補正 |
| 景観の配置 | 180ms | 乱数で木840・草13,500・遠景38,000などの候補を作り、候補ごとに陸地・生物群系・ランドマーク・道・城・川などを判定 |
| JSの解析・コンパイル | 152ms | 大きな数値配列のリテラル |

CPU4倍制限ではこれが約2.3秒になり、ページ表示から人物選択までの約5.8秒のうち、受信を終えた後の約3.1秒の大半を占めていた。

## 対策：結果をビルド時に作り、実行時は読み戻すだけにする

`node scripts/build.mjs && node scripts/bake-world-data.mjs`（`--check` で差分だけ確認）。書き出す前に実行時の展開処理で読み戻し、元と1ビットでも違えば書き出さない。

- **海岸**（`shared/paleo-coast-baked.mts`）：元のラン（バイト列）と、補正で変わる2つの矩形（旧い湾：地球の格子の370×325、山すそ：ワールドの格子の182×110）の最終値。矩形は補正前後の差から求めるので、補正の条件を二重に持たない。実行時は展開・行の写し・矩形の上書きだけ。計算は `shared/paleo-coast-build.mts` に移し、実行時は読み込まない。
- **山・城の地表**（`shared/camp-mountain-surface-baked.mts`、`shared/castle-surface-baked.mts`）：高さは小数2桁（山）・3桁（城）の値なので、整数の差分（ゼロは null）として持つ。10の累乗での割り算は正しく丸められるため、戻した値は元の数値と同じ倍精度の値になる。null・キーの順序も元のまま。
- **景観**（`shared/scenery-scatter.mts`、`shared/scenery-answers-baked.mts`）：配置の計算はそのまま残し、重い15種類の問い（陸地か、生物群系、ランドマーク・冒険区域・道・湾・城・洞窟まわり・山の川・資源・出発地点との距離）の答えだけを、問われた順に記録する（はい／いいえはビット、生物群系は1バイト、合計約20万件で98KB・gzip 14KB）。実行時は乱数と座標の計算をし、答えを順に読み戻す。答えの数が合わなければ読み込みを止める。配置の結果（約7,900件）をそのまま持つと約0.3MB増えるため、この形にした。
- 文字列は16進。1つの文字列リテラルは数値配列より解析がはるかに軽く、HTTP圧縮ではbase64より小さい（gzip・brotliとも）。

`tests/world-bake.test.mjs` が、元データと計算から作り直した結果と書き出したデータを照合する（海岸の2つの格子はバイト一致、地表は全要素が `Object.is` で一致、景観は答えが一致し、読み戻した配置がキーの順序・undefined の値まで一致）。入力やコードを変えたのに書き出し直していないと、このテストと実行時の照合で止まる。

## 結果

| | 変更前 | 変更後 |
| --- | --- | --- |
| `collision`+`terrain`+`world` の読み込み（Node、制限なし） | 約600ms | **約180ms** |
| 起動JS（runtime-main） | 6.91MB、gzip 1.16MB | **5.21MB、gzip 0.85MB**（brotli 0.64MB） |
| データ部分のgzip（海岸＋山＋城） | 749KB | 463KB |

ブラウザ（持ち運び版、Windows Chrome・390×844・CPU4倍・10Mbps／50ms・空キャッシュ、各2回。実スマホではない）：

| 指標 | 変更前（頭部r08採用後） | 変更後 |
| --- | --- | --- |
| ページ表示→人物選択の準備完了 | 5.65〜5.75秒 | **3.42〜3.54秒** |
| ゲームモジュールの準備完了 | 5.34秒 | **3.02秒** |
| 起動JSの受信完了 | 1.63秒 | 1.39秒 |
| 確定→洞窟で操作可能 | 5.88〜6.02秒 | 5.91〜5.94秒（変化なし） |
| 確定→通常世界の操作有効化 | 19.26〜19.43秒 | 19.52〜19.94秒（変化なし、ばらつきの範囲） |

洞窟から先は対象外（通常世界の読み込みは別の課題）。記録 `output/playwright/delivery-r01/bake-net-r0*`、パッケージ `output/bake-local-a01`。

## 検証

- 全体1,449件中1,445件合格・失敗0・条件付き4件未実行。`npm run check`（型・strict・605 JS構文・依存境界）合格。サーバー（Node）・公開MMOのWorker・テストも同じ書き出したデータを読む。
- 見た目・動作の変化はない：海岸・地表・景観は元と同じ値で、元の計算と照合している。
- 公開MMOのWorker（wrangler の空実行で測った送信量）：8,491KiB／gzip 1,077KiB → **5,251KiB／gzip 694KiB**。Workers Free の上限（gzip 3MB）に余裕が増えた。元のデータモジュールは `shared` ごと写される作業用フォルダーには残るが、`main` からたどれないので送られない。
- 作り直した持ち運び版（`output/bake-local-a01`）と公開MMO版（`output/bake-mmo-a01`、隔離Miniflare）で、開始→洞窟→通常世界→実タッチの移動・停止を確認（`output/playwright/delivery-r01/bake-packages-r01/`）。
- 元のデータモジュール（`paleo-coast-data`・`camp-mountain-surface-data`・`castle-surface-data`）は生成元として残し、書き出しとテストだけが読む。生成スクリプト（`scripts/build-paleo-geography.py` など）は変えていない。データを作り直したら `node scripts/bake-world-data.mjs` を実行する。

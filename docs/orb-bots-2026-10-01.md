## ピクミンの挙動の調査

一次資料：

- [任天堂 ピクミン3 操作ガイド](https://www.nintendo.com/eu/media/downloads/games_8/quick_start_guide/QuickStartGuide_WiiU_Pikmin3_EN.pdf)：種類の切替、投げる、笛で集める、隊列の操作を確認。運搬や戦いなどの仕事と、種類ごとの特徴がある。
- [任天堂 ピクミン4 ダンドリ指南 vol.1](https://www.nintendo.com/jp/switch/ampya/dandori/vol01/02.html)：笛で呼び戻すことと、危険への対応。
- [任天堂 ピクミン4 ダンドリ指南 vol.3](https://www.nintendo.com/jp/switch/ampya/dandori/vol03/02.html)：ヒマジン笛で仕事をしていない仲間を呼ぶ。仕事中かどうかで集合の扱いが異なる。
- [任天堂 ピクミン4](https://www.nintendo.com/jp/switch/ampya/index.html)：仲間を率いて探索し、種類の特性に応じて協力する基本構成。

参考にするのは「種類を選ぶ→手に持つ→狙った方へ投げる→呼び集める→隊列でついてくる」という関係。ピクミンが常に着地直後に自動で戻るという調査結果ではない。今回のbotはユーザー指定に合わせ、仕事や攻撃に留まらず、着地後は必ず持ち主へ自動で戻る。任天堂のモデル・画像・音声は流用しない。

## 全種類と制作方針

| 種類        | 添付画像の顔 | 外観                               |
| ----------- | ------------ | ---------------------------------- |
| しろbot     | ＾＾         | 乳白色の丸い体と黒い山型の目       |
| あおbot     | ＞＜         | 鮮やかな青い丸い体と黒いくの字の目 |
| みどりbot   | ＋＋         | 緑の丸い体と黒いプラスの目         |
| むらさきbot | ○○           | 紫の丸い体と黒い輪の目             |
| オレンジbot | －－         | オレンジの丸い体と黒い横線の目     |

添付の丸いシルエットを優先し、画像にない手足・口・葉・アンテナは足さない。直径約28cmの持てる大きさ。浮遊で済ませず、体を少し潰して弾む待機・歩行・走行、手の上での仕草、飛行、着地、合流の7動作を制作する。五つとも個別参照画像から復元する。一体の球を色替えして五体と扱わない。

原画像は `assets/orb-bots/source/user-reference.png` に無加工で保存。各色をbuilt-in imagegenで独立した正面寄りの全身・透過画像へ整理し、ローカルTRELLIS-2 → 元表面を保った軽量化 → 2骨のスキンと7動作 → exact GLBを検証する。失敗した復元と修正前の版を保持する。

## 操作と同期の仕様

- 各プレイヤーに各色1匹、合計5匹。5人参加なら25匹。自分のbotだけを持てる。
- Cで選択中の近いbotを左手に乗せ、もう一度Cで前へ投げる。Zで種類を選ぶ。色ボタンでも選べる。
- コントローラーは左スティック押し込みで持つ／投げる。メニュー「botたち」で全種類を選択。Q／十字キー↑／「呼ぶ」で集合。
- 持ち上げ300ms、投擲の予備動作260ms、飛行900ms、着地420ms、合流300ms。サーバーの既存操作間隔450msを守る。全員が同じサーバー時刻で飛行・着地を表示する。
- 飛距離は最大8m。壁・海・通れない崖の手前へ制限し、放す瞬間にも再検査する。着地点を線と小さい輪で表示する。
- 着地後は持ち主の後ろへ経路をたどって戻る。呼び戻しでも飛行や420msの着地動作を中断せず、地上の仲間へ集合を指示する。
- 渡れる川・湖では下側6cmを水中に置いて浮かび、水面下へ消えずに戻る。橋の上では橋の床を優先する。海へ投げ出すことはできない。
- 既存の戦闘・採集・食事・撫でる操作を始めると、手のbotを安全な地面へ戻す。乗り物・ダウン中は待機し、降りた後に再合流する。
- ワープは持ち主の安全な足場へ合流する。動的な障害物で5秒以上閉じ込められた場合も、衝突検証済みの合流位置へ復帰する。通常の帰り道は歩行する。
- botの一時的な位置・投擲状態は保存へ追加しない。切断時に所有分を除去し、再接続では5種類をそろえて再生成する。プレイヤーの持ち物や進行は変更しない。

## このホストの生成経路

既存CUDA版v0.8.1はWindows Code Integrityにより `ggml-cuda.dll` の読み込みが拒否された。セキュリティ設定・除外・署名チェックを変更せず、同じプロバイダーの公式v0.8.1 Vulkan配布を別の作業ディレクトリへ配置した。

[公式Vulkan配布](https://github.com/pwilkin/trellis.cpp/releases/download/v0.8.1/trellis-vulkan-windows-x64.zip)、ZIP SHA-256 `d6c70678635f5367f9aa93261e9310e7c0c327ca8395399cf2ef869ccc2e72ba`。NVIDIA RTX A1000 6GBはVulkanのGPU 1。GPU 0はIntelであり、最初の試行は中断・保持した。

白の1024復元ではHR形状工程が5/12段階で1,067秒、その後の段階が約280秒ずつかかり、テクスチャ工程にも進んでいなかった。元のCUDA設定のままの最高解像度は、このホストの利用可能なVulkan経路には実用的でないと判断。未完成のログを保持して中断し、全5種類を同じ512復元・4096アトラス・seed42で検証する。採用面数は固定せず、denseとの両方向の表面誤差と実物の輪郭・顔で決める。単純な丸い体という題材でも、粗いプリミティブへの置換はしない。

## 表面の修正と保持した履歴

白のrig r01は、TRELLISのdense段階から目が頭上にも複製され、正面の山型も崩れていた。数値検査だけでは採用せず、実GLBとdenseの画像を残して不採用にした。r02は復元した丸い表面を保持し、無加工の制作参照PNGから黒い目の画素を投影して、新しいUVアトラスへベイクしている。球や目の立体をプリミティブで作り直してはいない。元のUV・生成材質は失敗版へ保持し、r02の配信材質では参照画像の顔と、照明を除いた指定の体色を使う。背面の一様な体色は参照からの推定。

青以降も同じ表面修正方式を使う。青の暗い体色を黒い目と誤認しないよう、色付きbotの顔の抽出は最大RGB成分で判定する。白は輝度で判定する。各体のdense形状・頂点・UV・SHAは別々であり、色だけを替えた共用メッシュではない。

主モデルの削減では元denseと両方向14,000点、遠景では主モデルと両方向10,000点を比較。低い面数から試し、p95と最大誤差の基準を満たした最初の面数を実物の見た目と照合する。遠景は主モデルと骨順・inverse bind matrices・骨の初期行列が完全一致。ゲームでは主モデルの骨・材質・7動作をそのまま共用する。

オレンジのr02は、黒い横線が深いくぼみとして復元され、目の周囲に折れ目が出たため不採用。r03の頂点移動だけの補修でも折れ目が残り、LOD検査も不合格。元denseには内側へ約1mm離れた重複した殻があった。r04以降は外側の元表面を保持し、内側の不要な殻を除去したうえで、目の2領域だけを元の境界へ拘束した三角形へ張り直す。奥行きは周囲の元表面から補間し、球などのプリミティブへ置換しない。補修境界とそれ以外の外側頂点は完全に保持。オレンジの削減誤差は、この意図的な補修後の表面との比較であり、元のくぼみとの一致を主張しない。

r04/r05は新しいUVの削除時にBlenderの古い参照が別のレイヤーを指し、誤ったUVが配信された。数値検査は通ったが実GLBの表示に黒い継ぎ目が現れたため不採用。r06でレイヤーを名前から取り直し、残すUV名も検査して修正。r02〜r05・途中失敗のログ・実物の画像・Blenderをすべて保持している。

## 再現手順

1. `assets/orb-bots/workflow/generate.py <colour> --attempt 01 --resolution 512`（白だけ最終attempt 03）。TRELLISを1体ずつ実行。
2. Blenderで `prepare.py -- <colour> --attempt 01 --revision 02 --reference-material`。白の最終attemptは03、オレンジはrevision 06と `--repair-eye-patch`。既存の版を上書きしない。
3. Blenderで `pad-material.py -- <colour> <旧revision> <新revision>` を実行し、白〜紫は02→03、オレンジは06→08へ既存UVの余白を補修。既存の版を上書きしない。`padding-preservation.json` と同じ頂点・UV・全クリップ・骨・LODの保持を照合する。
4. `validate.py <colour> --revision <番号>` で主モデルと遠景の全頂点を120Hzで確認。最終の番号は `assets/orb-bots/revisions.json`。
5. `make-preview.py`、`qa-viewer.mjs` と既存の `assets/rimo-neko/workflow/render-review.py` でexact GLBの7方向、7動作、neutral/clay、操作可能なオフラインビューアーを検査。
6. 実物を目視してから `record-review.py` に所見を渡す。5体がそろってから `stage.mjs` でゲームへ登録。このスクリプトは未採用候補の初回配置／余白修正版への更新専用で、採用後には再実行しない。
7. `scripts/qa-orb-bots.mjs` の実Chromeとゲーム同期検証・画像確認後に `adopt.mjs`。今回の再読込／表示の継続検証は `qa-orb-reload.mjs` と `qa-orb-layout.mjs`、証拠の集約は `collect-game-evidence.mjs`。`archive.py` は5体それぞれの正本ライブラリへ原画像・dense・失敗版・Blender・QAを保存し、全ファイルのSHAを照合する。

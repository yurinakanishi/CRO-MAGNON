# 通常世界への入場準備と到着時の停止を減らす（2026-10-11）

ユーザーの選択「性能改善の根本課題の残りも進める（見た目を変えずに。入場条件のように方針の判断が要るものは案を出して確認）」による。[配信用変換](delivery-cooking-2026-10-11.md) の「残る根本課題4：通常世界へ入る条件」の調査と、その途中で見つけた準備と到着時の無駄の修正。

測定はすべて持ち運び版をWindows Chrome（ヘッドレス、ANGLE D3D11、KHR_parallel_shader_compileあり）で、390×844・CPU4倍・10Mbps／50ms・空キャッシュで開いた値。実スマホではない。PCの負荷が時間とともに変わるため、比較は変更前後のパッケージを1回ずつ交互に実行した。

## 入場条件は変えない（対象は妥当）

通常世界は、到着地点から半径82m以内の床・景観・ランドマークのテンプレート（このとき15件）を待ってから入場を許す。15件はどれも到着直後の画面に入る位置にある（景観6〜20m、資源8〜13m、洞窟と山）。確定から約6.3〜15.7秒の受信（約9.7MB）は回線の速さで決まっていて、入場条件を絞ると到着直後に見える物が欠ける。条件はそのままにし、受信の後の準備と到着時の停止を減らした。

## 原因1：準備の画面外描画が、全シェーダーをもう一組作っていた

`WorldRenderer.prepareEntry()` は、到着の最初の画面のシェーダーを `compileScene()` で並列にコンパイルした後、テクスチャを送るために8×8の画面外ターゲットへ1回描いていた。Three.js r185は、通常のレンダーターゲットへの描画では、出力をリニアのまま・トーンマッピングなしにした別のシェーダーを使う（`WebGLPrograms.getParameters`・`setProgram`）。このため画面外描画は、画面用にコンパイルしたばかりの材質をもう一度コンパイルし、描画の場でリンクの完了を待っていた。

- 計測（`output/head-lowpoly/tools/prepare-profile.mjs`、GLの呼び出しを記録）：準備中に作られたプログラム52個のうち21個が8×8の描画で作られ、作った直後に `getProgramInfoLog` で合計1,241msメインスレッドを止めていた。21個とも、その後は一度も使われない。
- 画面用のプログラムの初回使用（ユニフォームの取得、頂点配列の作成）は、結局ゲーム開始後の最初の画面で起きていた。

**修正：** `canvasProgramTarget()`（`src/context-recovery.ts`）。Three.jsが自分のXR用ターゲットに付ける印（`isXRRenderTarget`）と、画面と同じ色空間を付けたターゲットは、画面と同じシェーダーで描かれる。準備の画面外描画はこのターゲットへ描くので、`compileScene()` が用意したプログラムをそのまま使い、初回使用・頂点配列・形状とテクスチャの転送を、洞窟を見ている間（接続の前）に済ませる。r185の内部の約束に依存するため、`tests/context-release.test.mjs` がThree.js本体のレンダラー（GLは代役）で、通常のターゲットでは別のプログラムが増え、このターゲットでは1つも増えないことを確かめる。描画で増えたプログラム数は `#world` の `data-world-prepared-programs` に出し、`scripts/qa-loading-cave.mjs` が0であることを確かめる。

描画をやめてテクスチャだけ `initTexture` で送る案も実装して測った。準備はさらに0.1〜0.2秒短いが、初回使用と頂点配列・形状の転送が接続後の到着の画面に残る（到着時の停止がわずかに増える）。準備を接続の前に済ませるという元の設計に合う方を採った。

## 原因2：自分の人物のシェーダーを、到着した画面で作っていた

到着した画面で新しく作られるプログラムを調べると（`output/head-lowpoly/tools/handover-state.mjs`）、自分の人物の頭と体、松明を握った手の体（`TorchGrasp` が手の形をモーフで加えたもの）だった。自分の人物は参加してから作られるので、準備の `compileScene()` には入っていなかった。CPU4倍で合計約185msの同期コンパイル。

**修正：** 準備の `compileScene()` のとき、洞窟の展示が使っている人物のテンプレートを見えないグループに入れて一緒にコンパイルし、終わったら外す。人物の個体はテンプレートの材質を共有するので（`character-assets.ts`）、そのプログラムがそのまま使われる。松明を握った形は、展示の人物が握っている形を共有するので、その形の代役（`graspStandIns()`、`src/torch-grasp.ts`）も一緒にコンパイルする。代役は描かずに捨てる。`tests/context-release.test.mjs` が、本物の人物の骨格と動作で、準備した場合は到着した人物が松明を持って描かれてもプログラムが1つも増えないこと、準備しない場合は増えることを確かめる。

到着した画面で作られるのは、新しく流れてきた地面の組み合わせ（雪の地形）のプログラム2つだけになった。

## 原因3：カメラ用の三角形格子の作成が遅かった

`MeshRayGrid`（カメラが壁を突き抜けないための三角形の格子）は、三角形ごとに配列を作り、頂点を可変長配列へ展開し、格子の番号を文字列にしていた。洞窟（74,458三角形）で洞窟の展示を表示する前（壁）と、到着した画面（通常世界の洞窟）の2回作る。格子の番号を整数に詰め、頂点を最初から型付き配列へ書くようにした。作る三角形・格子・頂点（float32）と、全ての光線の答えは元と同じ（`tests/mesh-ray-grid.test.mjs` が元の作り方と洞窟・城で1要素ずつ照合し、2,000本の光線の距離が一致）。作成時間は洞窟で51.4→10.2ms（Node・制限なし、7回の中央値）。`scripts/qa-mountain-river.mjs` は格子の文字列キーを直接読んでいたので、`grid.cell(x, z)` に変えた。

## 残り（変更していない）

到着時の停止（CPU4倍で約1秒）は、次のものが残る。

- 「世界へ進む」を押した処理での音の開始。最初の `AudioContext` の作成がこの環境で505ms、洞窟の残響の作成が約115ms（`output/head-lowpoly/tools/audio-init-split.mjs`）。iPhoneでは押した処理の中で音を開始する必要があるので、作成そのものは移せない。押した処理で接続を先に始め、その要求の通信中に音を開く順序も試したが、応答は押した処理が終わるまで処理されないため差は往復1回分（約50ms）にとどまり、交互3回で差が見えなかったので戻した（`ab-final-r4*`・`ab-audio-r4*`）。
- 接続の開始時の状態の作り直しと表示（約200ms）、山のもう一方の詳細度の詰め込み（約190ms）、HUDの描画（約155ms）。
- 新しい地面の組み合わせが流れてきたときの地形シェーダー。
- 受信（約9.7MB）は回線で決まる。洞窟の画像の受信が終わってから通常世界の受信が始まるまで約1.2秒、回線が空いている。洞窟を先に見せるという意図的な順序なので、変えるかは方針の判断。

## 検証

- 全体1,452件中1,448件合格・失敗0・条件付き4件未実行。追加したテスト：`tests/mesh-ray-grid.test.mjs`（元の作り方との照合）、`tests/context-release.test.mjs` の2件（画面外ターゲットがプログラムを増やさないこと、松明を持って到着した人物がプログラムを増やさないこと。どちらも、そうしない場合に増えることも確かめる）。`npm run check`（型・strict・606 JS構文・依存境界）と `npm run format:check` 合格。
- 実Chrome：`scripts/qa-loading-cave.mjs` 合格（`output/playwright/entry-qa/loading-cave-r01/`）。準備の描画で増えたプログラム0、準備843ms。同じQA（制限なしのローカルChrome）で、通常世界の読み込み中の洞窟の最大フレーム時間は2026-10-10の記録の1,333〜1,375ms（準備2,053ms）に対し242ms。ビルドが異なるので参考値だが、元の停止は準備の描画の1.24秒（CPU4倍）と合う。
- 持ち運び版（`output/entry-local-a04`）と公開MMO版（`output/entry-mmo-a01`、隔離Miniflare）で、開始→洞窟→通常世界→縦持ちの実タッチ移動・停止を確認（`output/playwright/delivery-r01/entry-packages-r01/`）。
- 見た目の変化はない：画面は同じシェーダーで描かれ、準備の描画は画面に出ない8×8のターゲット、見えないグループと代役は描かない。カメラの格子は元と同じ値。
- `scripts/qa-mountain-river.mjs` は、洞窟の展示（2026-10-07）以降の開始手順（「進む」を押さない）と、まとめた配信（`src/world3d.js` を書き換える前提）に合っておらず、変更した行より前（通常世界の準備完了の待ち）で止まる。以前からの状態で、格子の読み方の置き換えは単体テストの照合で確かめた。
- 未検証：実Android／iPhone、実回線、物理パッド、5人接続（モデル・動作は変えていない）。既存の3000／8787／4173、保存、公開、展示配布、commit／pushは変更していない。

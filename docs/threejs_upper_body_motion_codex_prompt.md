# Three.js製MMOに「上半身だけのカメラ操作」を追加する

調査日: 2026-09-29  
対象: 既存のThree.js製3DオープンワールドMMO「クロマニョンMMO」  
用途: Codexへの調査・設計・段階実装・テスト指示

## 1. 依頼

既存リポジトリを読み、Webカメラによる上半身ジェスチャー操作を、既存操作を残した追加モードとして実装してください。

展示会では、ゲームコントローラーの操作に不慣れな来場者が、操作への抵抗感からゲームを触らないケースがありました。解決したいのは、モーションキャプチャそのものではなく、**コントローラーを知らない人でも、画面を見たまま遊び始められること**です。

単独の姿勢推定デモを作って終わらず、既存の移動・アクション・カメラ・オンライン同期に統合してください。ただし、大規模な作り直しや別エンジンへの移行は行わないでください。

調査で確認できた事実、今回の設計案、実機で検証すべき仮説を区別してください。この文書にある操作割り当てや数値は、明示的に必須としたもの以外は初期案であり、実測済みの推奨値ではありません。

## 2. 必須条件と禁止事項

### 必須条件

- **上半身だけで操作を完結**させる。肩・肘・手首を中心に使い、腰・膝・足首・足の検出を操作成立条件にしない。
- **利用者は画面正面を向いたまま**でよい。顔や体を左右に向ける、振り返る、首を傾ける、視線を外す操作を要求しない。
- 座った状態でも、必要な上半身と手が映れば利用できることを目標にする。立位・歩行・足踏み・実際のジャンプ・しゃがみを要求しない。
- 普通のRGB Webカメラ1台で開始する。VR機器、深度カメラ、専用センサー、装着機器を必須にしない。
- カメラ映像の認識は原則ブラウザ内で行う。外部AI APIやインターネット接続を基本操作の必須条件にしない。
- キーボード・マウス・ゲームパッドの既存操作を残す。カメラ操作を無効にすれば従来の状態に戻れるようにする。
- 人物や手を見失ったら、誤操作の継続よりも停止を優先する。
- 既存の衝突判定、移動速度、攻撃間隔、アニメーション、クライアント予測、サーバー検証を維持する。

「右を向く操作を使わない」とは、**人間が右を向く動作を入力にしない**という意味です。ゲーム内キャラクターの左右旋回は必要です。旋回は手の動きなどから生成してください。

### 今回行わないこと

全身の骨格をアバターへコピーするモーションキャプチャ、指一本ずつの操作、顔認証、感情推定、頭部追従カメラ、音声操作は今回の必須機能ではありません。追加モデルを最初から全部動かさないでください。

毎フレームのJev呼び出し、映像のサーバー送信、ゲームエンジンの置換、通常操作の削除、性能を測らないままの画質低下も行わないでください。

## 3. 最初に既存コードを調べる

最初に`AGENTS.md`などの作業指示、README、依存関係、ロックファイル、テスト、未コミット差分を確認してください。利用者の作業中の変更を上書き・巻き戻ししないでください。

以下を実際のファイル名・関数名とともに整理してください。

1. Three.jsのバージョン、WebGL/WebGPU等の描画構成、描画ループとシミュレーション更新。
2. JavaScript/TypeScript、UIフレームワーク、ビルドツール、Workerの組み込み方法。ReactやNext.jsを決めつけない。
3. キーボード・ゲームパッド入力から移動・旋回・ジャンプ・攻撃・インタラクトに至る経路。
4. カメラの追従、手動回転、障害物回避、Pointer Lockとの関係。
5. 入力の送信形式・頻度、プレイヤー操作の権限、通信切断時の処理。
6. 既存のメニュー、チュートリアル、設定、デバッグUI、テスト用シーン。
7. カメラ・MediaPipe・Jevの既存実装の有無。

最小の入力拡張ポイントを選び、無関係なシステムを変更しないでください。ファイルが存在しないのに、推測したパスやAPIを既存実装として扱わないでください。

既存設計の範囲で判断できることは進めてください。実機カメラやAPIキーがなくても、入力変換・状態機械・モックテストの実装を止める必要はありません。ただし、未実施の実機検証を成功と報告しないでください。

## 4. 調査で確認した技術と事例

以下の一次資料を確認し、実装時には導入するバージョンの型定義・ソースと照合してください。参考資料は末尾にあります。

| 資料・事例 | 確認できること | 今回への適用と限界 |
| --- | --- | --- |
| MediaPipe Pose Landmarker Web公式資料 [R1][R2] | ブラウザ向けAPI、33点の姿勢推定、モデル・設定 | 第一候補。ただし上半身が画面に収まる構図での操作精度は実測が必要 |
| Google公式Worker実装 [R3] | Worker内でのPose Landmarker、CPU/GPU選択、ImageBitmap入力 | 処理分離の実装参考。ゲームとの同時実行性能を保証するものではない |
| BlazePose論文 [R4] | リアルタイム人体姿勢推定の設計 | 技術的な根拠。論文中の端末性能を今回のゲームFPSへ転用しない |
| BlazePose GHUMモデルカード [R5] | 想定用途、遮蔽・照明等の制約、深度推定の限界 | 単眼の深度を実測距離として扱わず、上半身構図を重点検証する |
| 1€ Filter、CHI 2012 [R6] | ノイズと遅延のバランスを調整する低負荷フィルター | 手首の揺れを抑える候補。分類器ではなく、強くかけすぎれば遅延する |
| Consumed Endurance、CHI 2014／NICER、2024 [R7][R8] | 空中操作の腕の疲労、姿勢や休息の影響 | 胸元の小さな動作と休める停止状態を優先する設計根拠。今回の操作案自体が実証済みという意味ではない |
| UCL MotionInput [R9] | RGBカメラのジェスチャーを既存ゲーム等の入力に変換する事例 | 入力変換層という設計の参考。Windows/DirectX向けであり、Web版ライブラリとして導入するものではない |
| TensorFlow.js Webcam Pac-Man [R10] | カメラ画像の分類結果でブラウザゲームを操作する公式例 | 認識とゲーム入力をつなぐ実例。転移学習による4クラス分類で、骨格ベースのMMO操作とは異なる |
| KalidoKit／Kalidoface [R11] | MediaPipeとThree.jsによる3Dアバター駆動例 | 共存する構成の参考。READMEでdeprecatedとされており、新規依存として採用しない |
| MoveNet／IncludeHealth [R12] | ブラウザ内姿勢推定の実例と別モデル | 比較候補。異なる姿勢・端末の実績は今回の上半身認識精度の保証ではない |
| Jev公式仕様・Doomデモ [R17][R18][R19] | テキスト／JSON状態からの構造化判断。公開仕様では画像・動画入力に未対応 | 姿勢推定の代替にはしない。曖昧な判断を比較する任意実験として分離する |

### 誤解してはいけない点

**「肩・肘・手首の6点だけを使う」ことと、「モデルが6点だけ推論する」ことは別です。** 標準のPose Landmarkerは33点を推定します。利用点を絞っても、そのぶんニューラルネットの計算が省略されるわけではありません。[R2]

カメラ解像度を下げることも、推論負荷が同じ比率で下がることを意味しません。モデル側の入力サイズは別に定められています。撮影・転送・前処理・推論・描画を分けて測ってください。[R2][R5]

また、上半身操作を設計できることと、現在のモデルがあらゆる上半身クロップを安定検出できることも別です。脚を画面外にした状態を必須テストにしてください。失敗時に「全身を映す」要件へ変更しないでください。

## 5. 採用方針

第一候補は`@mediapipe/tasks-vision`の**Pose Landmarker Lite**です。まず肩・肘・手首の2D位置と信頼性情報で成立させてください。

ゲーム操作の判定は、最初は普通のコードと状態機械で実装します。連続移動と単発アクションを分け、Jevは基本操作の経路に入れません。

```text
Webカメラ
  ↓ 新しいフレームだけを、上限頻度で取得
推論Worker／Pose Landmarker Lite
  ↓ 上半身のランドマーク・信頼性・時刻
利用者選択／正規化／平滑化／キャリブレーション
  ↓
移動判定 + アクション状態機械 + 安全停止
  ↓
MotionInputAdapter
  ↓
既存の入力・移動・戦闘・同期処理
```

認識モデルは薄いアダプター越しに利用し、ゲームコードをMediaPipeの配列形式に密結合させないでください。ただし、比較のためだけに多数のモデルを同時導入することは避けてください。

Liteで上半身認識が不足する場合は、順に構図・余白・信頼性条件・Fullモデルを比較します。それでも不足する場合に限り、MoveNetやHand Landmarker単独構成を小さな検証で比較してください。[R12][R20]

Hand Landmarkerへ変更する場合、肩座標が得られる前提を残してはいけません。画面内の較正済み領域などへ座標基準を変更する必要があります。いずれも精度とゲーム同時実行時の負荷を測定してください。

## 6. 操作設計の初期案

以下は実装開始用の案です。必須条件を守ったまま、利用者テストで改善してください。

### 6.1 左手で移動、右手でアクション

最初は、**左手＝移動・旋回、右手＝アクション**という役割分担にします。設定で左右を入れ替えられるようにしてください。

同じ腕を「移動の腕振り」と「パンチ攻撃」の両方に使う案は、初期実装に採用しません。移動中の攻撃を分離して認識できることを優先します。

腕を伸ばし切る、肩より上で維持する、激しく振り回す必要のない範囲にしてください。頭や胴体の傾きは操作値にしません。

### 6.2 移動：胸元の小さな仮想スティック

左肘を体の近くに置き、手を楽な位置へ構えた状態をニュートラルとして較正します。そこから手首を動かす方式です。

| 左手の動き | 入力 |
| --- | --- |
| ニュートラル | 停止 |
| 少し上へ動かす | 前進。変位に応じて入力強度を調整 |
| 左右へ動かす | 左右旋回 |
| 上＋左右 | 前進しながら旋回 |
| 手を下げて休止領域に入れる | 前進・旋回とも停止 |
| 必要な点が不確か／画面外 | 前進・旋回とも停止 |

ここでの「上」は画像内の上下です。カメラへ手を突き出す奥行き操作ではありません。

初期版は前進・停止・旋回・その場旋回を優先し、手を下げる動作を後退へ割り当てないでください。休もうとすると勝手に後退する設計を避けるためです。後退が展示シナリオ上不可欠なら、休止と重ならない明示的な操作を別途設計し、理由を記録してください。

入力中にニュートラル位置が手を追いかけて移動しないようにしてください。再較正は停止状態で明示的に実施します。

休止領域から復帰する際も、途中の位置から突然動き出さず、一度ニュートラルへ戻してから有効化してください。

### 6.3 アクション：右手の分離された領域

右手も胸元にホーム位置を設け、近くの異なる領域への移動で操作します。画面上に現在の手の位置と操作名を表示してください。

| 右手の動きの初期案 | アクション |
| --- | --- |
| ホームから右側の領域へ | 攻撃 |
| ホームから上側の領域へ | ジャンプ |
| ホームから左側の領域へ | 調べる・拾う・撫でる等、既存のインタラクト |
| ホームへ戻る | 次の入力を受け付ける準備 |
| 下げて休める／見失う | アクションなし |

各領域を十分に分離し、同時に2種類のアクションが確定しないようにしてください。斜めの境界付近は無理に分類せず保留します。左右入れ替え設定では表示・領域・操作手の関係も整合させてください。

領域へ入っただけでは即実行せず、短時間の安定を確認します。初期値は例えば200ms程度とし、UIに確定までの進捗を示します。これは未実測の開始値です。

一度発火したら、ホームへ戻るまで同じ動作を連発しないようにしてください。ゲーム側のクールダウンと、認識側の再入力条件は別に扱います。

高速パンチ・両手を頭上へ上げるジャンプ・腕振り歩行は追加実験に留め、最初から必要条件にしないでください。単眼カメラの奥行き推定を実測のセンチメートルとして扱わないでください。[R5]

### 6.4 インタラクトの意味を変えない

「拾う」「調べる」「撫でる」などは既存の対象選択・近接条件を利用してください。ジェスチャー側に別の対象選択ロジックを複製しないでください。

対象がない場合は何もしません。インタラクトが失敗したから代わりに攻撃する、という暗黙のフォールバックは作らないでください。既存の文脈別アクションがある場合はそれを呼びます。

### 6.5 説明は短くする

初期チュートリアルは「左手で移動、右手でアクション」「手を戻すと停止」という程度の短い説明と、現在の入力を示すUIにします。

開始・終了・再較正は大きな画面ボタンを用意し、展示スタッフがクリックできるようにしてください。基本プレイ中にゲームパッドを握る必要がないことを優先し、全メニューのジェスチャー化は今回の必須範囲にしません。

## 7. 認識・座標・信頼性

### 7.1 対象点

Pose Landmarkerでは、肩・肘・手首に対応する点を使います。現行仕様の左右肩11/12、左右肘13/14、左右手首15/16を実際のAPIと照合してください。[R2]

脚や腰が検出されなくても、それだけで操作を無効にしないでください。一方、見えていない手の推測座標を信頼して入力を作ってはいけません。

顔を向き入力として使用しません。ただし、姿勢検出のため頭部を含む構図が必要になる場合があります。「顔の向きを操作に使わない」と「顔を映してはいけない」は別です。[R5]

### 7.2 座標系と鏡像

画像座標、プレビューの鏡像座標、人物基準の操作座標、ゲームの移動座標を分離してください。

プレビューは鏡のように見える表示を基本としますが、CSS反転と入力値の反転を二重に適用しないでください。モデルの解剖学的な左右と画面上の左右を混同しないでください。

肩幅で正規化する場合は、例えば次のように、まず縦横の縮尺が一致する座標へ変換します。

```text
p = (landmark.x × imageWidth, landmark.y × imageHeight)
c = 左右肩の中点
s = 左右肩間のピクセル距離
r = (手首位置 - c) / s
u = r - キャリブレーション時のニュートラル相対位置
```

鏡像変換は必要な箇所で一度だけ適用します。肩幅が極端に小さい、値がNaN、必要点が不確か、座標が不連続に跳んだ場合は無効にします。

身体全体が少し横に動いただけで旋回しないよう、手首の人物基準の相対変位を使用してください。肩幅等の基準値も安定化しますが、入力中に勝手にキャリブレーションを更新してはいけません。

ROIをクロップする場合は、元画像への座標変換を明示し、アスペクト比を崩して引き伸ばさないでください。

### 7.3 平滑化とデッドゾーン

まず実際のジッターを確認し、必要に応じて1€ Filterなどを採用してください。静止時の安定と動作時の遅延を両方測ります。[R6]

正規化した入力の中央にデッドゾーンを設け、開始閾値と解除閾値に差を持たせます。閾値付近で移動と停止が交互に発生する状態を防いでください。

推論結果・操作値・ゲームカメラの全段に強い平滑化を重ねないでください。安全停止は平滑化を迂回して処理します。

### 7.4 人物の取り違え

初期構成は`numPoses: 1`としますが、**これはプレイヤーの本人固定を保証する設定ではありません**。[R1][R5]

中央の操作領域、肩の中点・大きさの連続性、必要点の信頼性を使って、背景の観客への切り替わりを抑制してください。ただし、これを顔認証や完全な同一人物追跡と説明してはいけません。

人物の切り替わりが疑われる場合は入力を止め、ニュートラル確認や再較正を要求します。操作していた人が退いた直後、後ろの人が自動で操作を引き継がないようにしてください。

## 8. 状態機械と安全停止

状態は、少なくとも次の責務を区別してください。名称は既存設計に合わせて変更可能です。

```text
OFF → STARTING → CALIBRATING → READY → ACTIVE
                       ↑         ↓        ↓
                       └──── PAUSED / TRACKING_LOST

各状態から ERROR / STOPPING → OFF
```

`READY`はモデル・較正が準備できた状態であり、即座に移動を開始する意味ではありません。ニュートラル確認などの明確な再開条件を設けます。

### キャリブレーション

頭・肩・肘・操作する手が映るガイドを表示し、両手を胸元の楽な位置に構えた安定状態を1〜2秒程度取得します。平均だけでなく中央値や外れ値除去を検討してください。

較正中はゲーム入力をゼロにします。検出できないまま待ち続ける画面にせず、どの部分が見えていないか、カメラ角度・照明・位置をどう直すかを案内します。全身を映すことを解決策にしないでください。

### 停止条件

移動に必要な肩・操作手の信頼性低下、フレームの更新停止、入力データの期限切れ、カメラ切断、Worker異常、タブ非表示、メニュー表示、利用者交代、モード終了では、対応する入力を無効化してください。

初期の期限切れ判定は「最後の有効フレーム取得から300ms以内に入力ゼロ」を目標とします。正常なメインスレッド／更新ループでのアプリ側目標であり、あらゆるフリーズ中の実時間保証とは区別してください。

明確な手の喪失・終了操作は期限切れまで待たず停止します。短い認識欠落を許容する場合でも、最後の前進を無期限に保持しないでください。アクションは不確かな間、常に新規発火を禁止します。

右手だけを見失った場合など、移動とアクションで必要な点が異なることを考慮してください。移動に必要な点が有効なら移動を残せますが、古い右手の座標で攻撃を発火してはいけません。

復帰時に古い押下・保留アクション・速度推定を再利用しないでください。フィルターも不連続な時刻を跨いで誤動作しないようにリセットします。

**MMO全体を一時停止させる機能ではありません。** カメラの喪失はローカル入力を止める処理として扱い、既存のサーバー同期、他プレイヤー、戦闘ルールを勝手に変更しないでください。

## 9. 単発アクションを重複実行しない

ジェスチャーは次のような状態遷移で確定します。

```text
HOME → CANDIDATE → CONFIRMED → WAIT_FOR_RETURN → HOME
```

時間条件はフレーム数ではなく経過ミリ秒で管理します。推論頻度が10Hzから20Hzへ変化しても、確定時間が変わってはいけません。

ジャンプ・攻撃・インタラクトはイベントとして一度だけ発行します。15Hzの認識結果の`attack=true`を60fpsの描画ループが繰り返し消費する設計にしないでください。

イベントにはセッションIDとイベントID、生成・元フレーム時刻を付けます。同じイベントの再適用、古いイベントの遅延実行、較正し直す前のイベントの流入を防いでください。描画停止中に溜まった古いアクションをまとめて実行しないよう、有効期限も設けます。

同一時点のアクションが競合したら、曖昧なものを発火しないことを原則とします。移動と単発アクションは独立させ、「前進しながら攻撃」「旋回しながらジャンプ」は成立させてください。

## 10. Three.jsと既存入力への統合

カメラ認識コードからプレイヤーMeshの`position`や`rotation`を直接書き換えないでください。既存の操作処理へ、通常入力と同等の操作意図を渡します。

以下は責務を示す概念例です。既存コードに同等の型があればそちらに合わせ、JavaScriptプロジェクトへTypeScriptを強制導入しないでください。

```ts
type MotionAction = 'attack' | 'jump' | 'interact';

interface MotionIntent {
  active: boolean;
  forward: number; // 初期版 0..1
  turn: number;    // -1..1
  sessionId: number;
  sampledAtMainMs: number;
}

interface MotionActionEvent {
  sessionId: number;
  eventId: number;
  action: MotionAction;
  sampledAtMainMs: number;
  emittedAtMainMs: number;
}
```

連続値を読む経路と、アクションイベントを一度だけ消費する経路を分けてください。デバッグ表示がイベントを先に消費してゲームへ届かなくなる構成も避けます。

既存入力がカメラ相対の移動ベクトルだけで表現されている場合は、カメラモード内の目標進行方向を管理し、既存の移動意図へ変換します。旋回と自動追従カメラが互いに増幅する循環を作らないでください。その場旋回時の向き変更も、既存のキャラクター制御へ適切に接続します。

既存キーボード・ゲームパッドとの入力所有権を明示してください。二つの入力を無条件に加算したり、カメラ開始時に別入力の押下状態を引き継いだりしないでください。スタッフによる明示的な停止や通常操作への切り替えを用意します。

MMOへは既存方式に従って入力またはゲーム状態を送ります。カメラ映像や骨格座標のネットワーク同期は追加しません。姿勢推定の頻度に合わせてネットワーク送信頻度を増やすことも避けます。

## 11. カメラ操作の自動化

カメラ操作モード中は、利用者による右スティック相当の視点操作を必須にしません。

既存の三人称カメラを利用し、キャラクターの進行方向または安定した目標向きの背後へ滑らかに追従させます。停止時の微小な入力ノイズで視点が揺れないようにします。

既存の壁・地形とのカメラ衝突回避を維持してください。急激な180度リセンター、首・顔・肩の向きによる視点回転、必要のないカメラ揺れは入れません。

減衰・旋回速度は`deltaTime`を用いて定義します。Three.jsの`MathUtils.damp`などはフレームレート非依存の処理の参考になりますが、角度では最短回転や角度の折り返しにも対応してください。[R16]

モードを終了したら元のカメラ設定へ戻し、通常操作に自動追従の変更を残さないでください。

## 12. 推論と描画を分離する

Pose Landmarkerの`detect`／`detectForVideo`は同期処理です。公式ガイドとWorkerサンプルを参照し、原則として推論をWorkerに分離してください。[R1][R3]

既存のThree.js描画ループを維持し、ゲーム全体のWorker移設やレンダラーの作り直しは行いません。認識用に別のゲーム描画ループを作ることも避けてください。

### 12.1 最初の試験設定

| 項目 | 初期案 |
| --- | --- |
| カメラ | 640×480、30fpsを希望値として要求。実際の取得設定を記録 |
| 音声 | 取得しない |
| モデル | Pose Landmarker Lite |
| モード | Web APIの`VIDEO` |
| 人数上限 | 1 |
| Segmentation | 無効 |
| 推論頻度 | 15Hzから開始。必要に応じ10／20／30Hzを比較 |
| 推論並列数 | 1。待ち行列を溜めない |
| Delegate | Worker内のCPU/GPUを両方比較 |
| 描画 | 既存の更新方式を維持。60fpsは目標であって保証ではない |

`640×480`等は厳密条件ではなく希望値にし、対応していないカメラで不必要に失敗しないようにします。[R13]

### 12.2 Backpressureとリソース管理

新しい動画フレームの取得には、対応環境で`requestVideoFrameCallback`を利用できます。これはゲーム描画の代替ではありません。未対応時は新規フレーム判定と上限頻度を備えたフォールバックを用意します。[R14]

推論中は次の処理対象を作成・投入せず、古いフレームを捨てます。`setInterval`で非同期処理を無制限に積み上げないでください。ImageBitmap作成前から多重起動を防ぎます。

Workerへは、実際のブラウザ・APIで対応する`ImageBitmap`等を転送します。HTMLVideoElementをそのままWorkerへ転送できると仮定しないでください。[R3]

フレームの取得、前処理、転送に要する時間も測定してください。GPU→CPUの読み戻しや必要以上のCanvasコピーを繰り返さないでください。

所有権を明確にし、正常終了・例外・途中終了のどの経路でもImageBitmap等を解放してください。終了時にはモデル、Worker、イベントリスナー、動画コールバック、MediaStreamTrackを処理します。[R3][R15]

### 12.3 時刻と古い結果

メインスレッドでのフレーム取得時刻、Worker内の推論時間、メインスレッドへの結果受信時刻を分けます。異なる実行コンテキストの`performance.now()`を無条件に引き算しないでください。

推論APIへ渡すタイムスタンプは、採用バージョンの仕様に合う単位・単調増加を維持します。セッションID・フレームIDを返し、再起動前の結果や順序が逆転した結果を破棄します。

フレーム取得時刻は、物理カメラの露光開始時刻とは限りません。ソフトウェア内の経路時間を測っただけで、動作から画面表示までの完全な遅延を測定できたとは報告しないでください。

### 12.4 CPUとGPU

Worker化はメインスレッドの同期ブロックを避ける方法であり、CPU/GPUの競合を消す方法ではありません。

GPU推論はThree.jsの描画と競合する可能性があり、CPU推論もCPU負荷を増やします。推論単体の速度だけで選ばず、ゲーム描画のフレーム時間と操作の遅延を合わせて評価してください。

Worker・WASM・GPUの互換性は、本番ビルドで検証します。GPU構成が動かなければCPU Workerを試し、無理にメインスレッドの高頻度推論へ切り替えないでください。

WASMマルチスレッド等のためにサイト全体へCOOP/COEPを安易に追加せず、必要性と既存機能への影響を確認してください。使えない機能を必須にせず、確認できた構成で動かします。

## 13. Jevの扱い

Jevを使えるかは検討対象ですが、**使うこと自体を目的にしません**。

調査時点の公式仕様では、Jevの入力はテキスト／JSONで、画像・音声・動画には対応していません。Doomの公開例も構造化されたゲーム状態を入力しています。[R17][R18]

したがって、Webカメラの認識はMediaPipe等で実施し、基本的な入力判定はローカルで完結させてください。

Jevの応答が構造化されることと、操作意図の判断が必ず正しいことは別です。Jevを使えば誤認がなくなる、応答遅延がなくなる、という前提は置きません。[R19]

### 任意実験としての分離

既存リポジトリにJev連携がある場合は再利用できるか調べます。ない場合は、MVPのためだけに新しい有料APIや大きなバックエンドを構築しないでください。

必要なら、認識結果を比較する`GestureDecisionProvider`等の薄い境界を設けます。Jevを実際に試すときは、最初は**判断を記録するだけでゲームを操作しないshadow mode**にします。

渡す候補は、正規化した手の変位・速度、短い時系列、認識信頼性、ローカル判定結果、実行可能なアクション等です。画像や生動画は送りません。必要最小限の情報にし、身体特徴を含むデータを「座標だから匿名」と断言しないでください。

Jevを試す場合も、移動値の毎フレーム制御はローカルに残します。低頻度の曖昧なアクション候補判断等に限定し、同時リクエスト数、タイムアウト、古い応答の破棄、費用上限、ローカルへの復帰を設けます。

APIキーをフロントエンドへ埋め込まず、許可済みのサーバー側経路を使います。利用者の明示的な許可なしに、課金を伴う外部APIを実行しないでください。キーがない場合は無効のままにし、基本操作を完成させます。

採否は、同一データでの誤発火・見逃し・遅延・費用の比較から判断してください。「AIを使ったから良い」という評価にしません。

## 14. UI、配信、プライバシー

「カメラで遊ぶ」「通常操作に戻す」「再調整」「終了」を分かりやすく配置してください。カメラは明示的な開始操作の後に起動します。

プレビューに、必要な上半身のガイド、現在の手の位置、ニュートラル、入力領域、確定待ち、追跡状態を表示してください。全身骨格の常時表示や大きな映像でゲーム画面を覆う必要はありません。

カメラ操作OFF時には、原則としてモデル・WASMのダウンロードやカメラ起動を行わない遅延読み込みにします。SSRがある場合は、サーバー評価時にブラウザ専用APIを実行しないでください。

### 展示会のネットワーク

カメラにはsecure contextと権限が必要です。`localhost`で動いても、別PCから`http://192.168.x.x`等で開く展示構成がそのまま同じ条件になるとは限りません。HTTPS、iframeのPermissions Policy、本番の配信経路を確認してください。[R13]

JSパッケージ、WASM、モデルのバージョンを対応させ、ロックファイルと配信アセットを固定します。実行時に`@latest`へ依存しないでください。モデルの出典、ライセンス、サイズ、識別可能なバージョンまたはハッシュを記録します。

可能な範囲でモデル等を同一オリジンから配信し、展示時に外部CDNが不調でも基本操作を妨げない構成にします。ただし、カメラ認識の外部通信が不要なことと、MMO自体が完全オフラインで動くことは区別してください。

### プライバシーと終了処理

録画・画像保存・骨格の継続保存はデフォルトで無効にします。外部解析やエラー監視へ画像・身体座標を混ぜないでください。映像非送信の設計であることを、ネットワーク検証でも確認します。

性能測定は必要最小限の集計値を中心とします。実映像やランドマークのテスト記録が必要な場合は、目的と保存方法を明示し、許可された資料のみを使います。

終了ボタン、画面遷移、初期化失敗、カメラ権限要求中のキャンセルにも対応します。終了後に遅れて権限が許可されても、取得したストリームを残さないでください。

権限拒否、カメラなし、他アプリ使用中、モデル取得失敗、WASM初期化失敗、Worker失敗、長い権限待ちを区別して表示し、通常操作に戻れるようにしてください。[R13]

## 15. 性能評価

最初にカメラOFFのベースラインを測り、その後、同じ端末・シーン・解像度・描画設定で比較します。単独の骨格デモが滑らかでも、ゲームへ統合した性能の証拠にはしません。

比較対象は、カメラ映像だけON、Lite＋CPU Worker、Lite＋GPU Worker、推論頻度10／15／20Hzを優先します。Fullや別モデルは必要時だけ追加します。

最低限、次を区別して記録してください。

- 描画のフレーム時間の中央値・p95、FPS、長いフレームの頻度。
- 推論時間、実効推論Hz、ドロップしたフレーム数。
- フレーム取得から結果受信、結果受信からゲーム適用までの時間。
- アクション確定のため意図的に待った時間、平滑化による遅れ。
- 上半身の有効検出率、追跡喪失回数、誤発火・見逃し。
- 起動時間、モデル読み込み時間、連続稼働時のメモリ変化。

ソフトウェア内の時刻差と、身体動作から表示までの遅延は別項目にします。必要なら実機の動画等で後者を検証し、実施していなければ未測定と書いてください。

初期の目標は、カメラOFFで60fps近く出る展示PCなら、カメラONでもその滑らかさを大きく崩さないことです。許容幅はベースラインを見て明示します。例えばフレーム時間中央値の悪化10%以内などを暫定指標にできますが、未検証の達成値として書かないでください。

負荷が高ければ、まず推論頻度、フレーム転送、不要なデバッグ表示、delegateを見直します。認識精度を確かめずに解像度を落とし続けたり、ゲーム全体の画質を黙って下げたりしないでください。

## 16. テスト

### 16.1 単体・モックテスト

合成ランドマーク列と仮想時刻を使い、カメラなしでも再現可能にします。

以下を重点的に検証してください。

1. 下半身の点がすべて無効でも、必要な上半身が有効なら操作できる。
2. 顔や胴体の向きだけを変えても、移動・旋回・視点入力が生成されない。
3. 鏡像表示と実際の左右操作が一致し、左右入れ替え設定でも成立する。
4. ニュートラルのノイズでは動かず、手を下げて休むと後退せず停止する。
5. 左手の移動が右手の攻撃と誤認されず、移動＋攻撃を同時に扱える。
6. 1回の確定でイベントは1回だけ。認識15Hz／描画60fpsでも重複しない。
7. ホームへ戻る前の再発火、領域の通過、境界の揺れで誤発火しない。
8. 信頼性低下、期限切れ、Worker応答遅延、古いセッションの結果で安全側へ移る。
9. 推論頻度や描画FPSが変わっても、確定時間や旋回速度の意味が変わらない。
10. メニュー・終了・再較正後に、以前の入力やイベントが残らない。

### 16.2 ブラウザ統合テスト

既存のテスト基盤を利用し、権限拒否、無映像、モデル404、Worker初期化失敗、繰り返しON/OFF、画面遷移、タブ非表示を検証してください。

モックやfake mediaで確認したことと、実際のカメラ映像で推論したことを分けて記録します。合成ランドマークテストの成功を、人体認識の精度確認の代わりにしてはいけません。

APIは存在していても本番バンドルでWorkerが起動しないケースを見落とさないよう、開発サーバーだけでなくproduction buildでも確認してください。

### 16.3 実機チェック

実機を使える場合は、次の場面を確認します。使えない場合は手順と未検証項目を残します。

- 座位と立位、胸から上中心の構図、脚・腰が完全に画面外の構図。
- 身長差、服装、背景、通常照明と逆光、速め／ゆっくりの操作。
- 手が画面外へ出る、顔の前を手が通る、観客が横切る、利用者が交代する。
- 前進＋旋回、前進＋攻撃、停止、ジャンプ、近接インタラクト。
- 2台以上の既存MMO接続で、カメラ操作プレイヤーの動作が従来どおり同期する。
- 少なくとも10分程度の連続試験と、次の来場者に交代する試験。

初心者テストでは、操作成功率だけでなく、説明後に自力で始められたか、停止方法を理解できたか、画面から視線を外さず操作できたか、腕を休められたかを確認してください。

数名の試験結果を万人への保証として扱わず、人数、条件、試行数、失敗内容を記録します。必要ならスタッフが操作しやすさを確認するチェックシートもMarkdownで作成してください。

## 17. 実装順序

### Phase 1: リポジトリ調査と計測準備

入力・カメラ・同期経路を把握し、変更予定箇所とベースライン計測方法を整理します。実測できる環境ならベースラインを保存します。

### Phase 2: カメラ非依存の入力変換

合成ランドマークを使って、正規化、較正、移動、単発アクション、安全停止、既存入力への接続を実装・テストします。

### Phase 3: 実カメラとWorker

Pose Landmarker Liteを追加し、カメラ取得、フレーム制御、Worker推論、リソース解放、初期化エラーを実装します。上半身構図で認識できるかを確認します。

### Phase 4: 展示UIと追従カメラ

開始・終了・再較正、短いチュートリアル、入力表示、利用者交代、モーションモード限定のカメラ追従を統合します。

### Phase 5: 実測と調整

CPU/GPU、推論頻度、ノイズ、誤入力、疲労、同期を確認し、採用設定と残る問題を記録します。

### Phase 6: 任意のJev比較

必要性と実行許可がある場合だけ、shadow modeで比較します。MVPの完成条件にしません。

## 18. 完了条件と成果物

### 必須の完了条件

- 上半身だけで基本的な移動・旋回・停止・アクションへ入力できる実装がある。
- 顔や体を左右へ向ける操作、脚の検出、実際の歩行を要求しない。
- 基本入力がローカルで動き、Jevや外部APIなしで利用できる。
- 描画と推論が分離され、フレームを無制限にキューへ積まない。
- 手や人物を見失っても、移動・攻撃を継続しない安全処理がある。
- 既存のキーボード・ゲームパッド・ゲームルール・MMO同期を維持する。
- 終了時にカメラ・Worker・関連リソースが解放される。
- 単発アクションの重複と、再起動前の古い結果の適用を防ぐ。
- テスト・計測手順があり、実施済み／未実施が明示されている。

機能を実装できたことと、展示PCでの認識精度・性能が合格したことは分けて報告してください。カメラを試せなかった場合は「実装済み・実機検証待ち」とし、「展示利用可能」と断定しないでください。

## 指定の読み方

- 2の「初期リロード前のアプデの洞窟」は、ページを開いて最初に通常世界を読み込む間に歩ける「アプデの洞窟」（[ローディング洞窟](loading-cave-2026-10-07.md)）とした。
- 3の「リロードする時」は、洞窟を通らずに世界へ入り直す読み込みとした：タイトルへ戻ってから再び始める（世界は読み込み済み）、部屋のリセット後、タイトルの「アプレノ洞窟に行く」、展示（LAN）の開始。ページを再読み込みした後の最初の入場は、従来どおりアプデの洞窟が読み込みの画面を兼ねる（ローディング画面を重ねない）。違う意図なら変更する。

## 1. OpenAI Dots

dotsの仲間9体（丸い5色・形の4種類）は、OpenAIが2026-09-29のDevDayで発表したAIエージェント「dots」のキャラクターを、ユーザー提供の参照画像（`assets/orb-bots/source/user-reference.png`・`assets/shape-bots/source/user-reference.png`）から制作したもの。

- 「友情出演」の最後に「OpenAI Dots」を追加（`TITLE_DOTS`、`src/title-credit-profiles.ts`）。dotsは常にゲームにいるので、マスコットの公開設定（`MASCOT_ROSTER`）に関係なく全ビルドに載る。
- 検索した範囲ではdots専用のXアカウントが見つからなかったため、リンクなしのカード（`profile: ''`）。`x.com/<handle>` 形式だけをリンクにする規則は変えていない。リンク先を指定されれば追加できる。
- Xのプロフィール写真の代わりに、ゲームが既にメニューで表示している3体の肖像（`public/models/orb-bot-{beret,triangle,white}/portrait.png`、無加工）を、ダイアログのアイコン背景色の上に並べた200×200のJPEG `public/title/avatar-dots.jpg`（8,640 bytes）。作成 `scripts/build-dots-avatar.py`、元画像と出力のSHAは `assets/title-credits/dots-avatar.json`。新しい画像生成・3Dモデル制作はしていない。
- 公開ビルド（`scripts/cloudflare-public-build.mjs`）が書き直す `title-credit-profiles.js` に `TITLE_DOTS` を含め、アイコンも配信対象にした。`scripts/verify-mascot-release.mjs`・`scripts/qa-cloudflare-release.mjs` に確認を追加。公開デプロイはしていない。

## 2. アプデの洞窟で「関わってくれた人たち」を開く

- 洞窟の見出しの右、「タイトルへ戻る」の左に「関わってくれた人たち」ボタン。タイトルと同じダイアログ（同じ人物・アイコン・Xリンク）を開く。既に洞窟にいるので、「アプレノ洞窟に残る壁画に…」の案内と「アプレノ洞窟に行く」は出さない（`contributorsDialogMarkup(…, { visit: false })`）。
- ダイアログが開いている間、洞窟はキー・スティック・Aボタンを読まない。Escはダイアログを閉じるだけ（タイトルへ戻らない）、矢印・スティックはダイアログ内の移動、Aは「世界へ進む」にならない。開いた時点で歩行・ドラッグを止める。閉じた直後のキーはすぐ効き、閉じる操作で押していたAは一度離すまで進まない。
- 幅440px以下（縦持ちのスマホ）では2つのボタンを縦に並べる。

途中のQA（r04）で、閉じた直後のフレームで押下中のキーまで消していた不具合を見つけ、消すのを「開いたとき」だけにした。

## 3. ローディング画面

### 出す場面

- **自分のワープ**：メニューの写真付き6地点、地図の焚き火、展示のワープ、「アプレノ洞窟に行く」で入った直後の洞窟へのワープ。自分の `warp` 要求にサーバーが応えて位置を移した状態（`warpSequence` の増加）を受け取ったその処理の中で表示するので、移動先が描かれる前のフレームは見えない。要求から15秒以内のワープだけを対象にし、他人のワープや、QAがサーバー側で位置を直接動かす準備操作では出さない。
- **洞窟を通らない入場**：タイトルへ戻って再び始める、部屋のリセット後、「アプレノ洞窟に行く」（世界の最初の読み込みから洞窟へのワープまで1枚の画面で続ける）、展示（LAN）の開始。QA用の `?autostart=1` はタイトルと同様に省き、従来の読み込み表示のまま。
- 最初の入場（アプデの洞窟）には重ねない。

### 何を待って外すか

`WorldRenderer.surroundingsReady()`：既存の到着（`arrival()`：自分の状態、足元の地面 `OpenWorldTerrain.arrive`、自分の人物の描画）の後、到着地点から82m以内のランドマーク（起動時の計画と同じ `criticalLandmarks`）が配置されるのを最大10秒待ち、画面の下で2フレーム描いてから外す。最短1.5秒（豆知識を読める長さ）。9秒を超えると次の豆知識へ切り替える。外れ始めた時点で操作を戻し、0.32秒でフェードする。待った地面の位置・ランドマーク・各段階の時間は `#world` の `data-arrival-landmarks` に出る。動物・他の人物・遠くの景色は従来どおり後から流れてくる。

- 画面は、待つ処理より先に1回描かれてから待ち始める（`nextPaint()`）。到着の処理は足元の地面を一度にまとめて組み込むので（これまでのワープでは毎フレーム少しずつ）、先に描かないと、画面が出る前に数秒止まって見え、出た直後に消えてしまう。止まっている間も炎の印の動きは止まらない（合成の処理で動くCSSアニメーション）。
- ワープの画面は、受け取った状態を `renderer.setState()` で反映した直後、同じ処理の中で出す。反映の前に始めると、元の場所の地面を待ってしまう。
- 画面が出ている間は移動・メニュー・カメラ・クリックを受け付けない（`playReady()` と画面のポインター遮断）。タイトル・人物選択・描画の失敗では即座に消す。
- ワープ先の地域名の表示（エリアバナー）は、画面が外れてから出す。

### 見た目

- 左上：「ワープ」と行き先の名前（入場時は「旅の準備」）。写真のある6地点は、その写真をぼかして暗くした背景にする（モンハンの行き先画像のように）。地図の焚き火は暗い背景だけ。
- 左下：「クロマニョン人の豆知識」の見出しと本文。30項目（`src/loading-tips.ts`）をシャッフル順に出し、同じものを続けない。
- 右下：揺れる炎の印と「読み込み中」。世界の最初の読み込みでは洞窟と同じ「世界を読み込んでいます N%」と進み具合の線。
- 縦持ちでは状態を豆知識の上に置く。動きを減らす設定では炎とフェードのアニメーションを止める。
- 実装は `src/loading-screen.ts`（`TipDeck`・表示時間の規則 `LoadingCover`・画面 `loadingScreenView`）、CSSは `src/style.css`。

### 重なり順の修正

`.game-viewport > [class]:not(…)` の規則（HUDを z-index 2 にまとめる）は、クラス1つの規則より詳細度が高く、`.render-error`（40の指定）と `.context-recovery`（45）も2に下げていた。ローディング画面がGPUの復元表示を隠さないよう、この規則から全画面の3つ（ローディング画面・描画の失敗・復元）を除いた。実Chromeの計測で HUD 2 < 手の操作 25 < ローディング画面 35 < 描画の失敗 40 < 復元 45（[4.](#4-アプデの洞窟自体の読み込みもローディング画面で追加指定) で洞窟の上へ移し、ローディング洞窟 40 < ローディング画面 42 < 描画の失敗 43 < 復元 45）。失敗と復元の表示は、CSSに書かれていた本来の重なり（タイトルや洞窟の上）で出るようになった。

## 4. アプデの洞窟自体の読み込みもローディング画面で（追加指定）

- 最初の入場で洞窟そのもの（洞窟のGLB・選んだ人物・壁画の画像）を読み込む間を、ワープと同じローディング画面で覆う。左上に「世界への旅支度／アプデの洞窟」、背景に洞窟の写真、左下に「クロマニョン人の豆知識」、右下に炎の印と「洞窟を準備しています」。最短1.5秒、9秒ごとに次の豆知識。
- 洞窟が描けた時点（`LoadingCave.load()` の完了）で画面を外し、洞窟に入ったら豆知識は出さない。そのあと通常世界を読み込む間は、従来どおり洞窟を歩いて壁画を見る（洞窟の表示・操作は変えていない）。
- 画面を洞窟の上に重ねるため、重なりを HUD 2 < 手の操作 25 < ローディング洞窟 40 < ローディング画面 42 < 描画の失敗 43 < 復元 45 にした。失敗は従来どおりローディング画面を消してから出る。
- 洞窟を準備している間は洞窟のボタンが画面の下になり押せない。Escでのタイトルへの戻りは効く。洞窟がすぐ読める環境（PCの再訪など）では、最短の1.5秒とフェードの分だけ洞窟が見えるのが遅くなる（`cave-playable` の計測点は変えていない）。
- 最初の指示を読み違え、洞窟の中にも豆知識のカードを出す版を作ったが、ユーザーの訂正で取りやめた（洞窟の中のカードとそのCSSは削除。両画面で使える部品として作ったカード `tipCard()` と共通CSS `.loading-tip` はローディング画面で使っている）。

検証（`output/playwright/loading-screen-20261011/r18/report.json`、10項目合格・エラー0）：洞窟の受信を止めている間、ローディング画面が出てから2msで描かれ、洞窟のボタンの位置で一番上にあるのがローディング画面であること、表示内容（見出し・洞窟の写真・豆知識・「洞窟を準備しています」）、受信を再開して洞窟が描けると外れ、洞窟の中に豆知識のカードがないこと、「世界へ進む」での入場では画面が出ないこと、続く城へのワープの豆知識が洞窟の読み込みで出たものと違うこと（同じ山札）。スマホ縦（390×844）でも同じ画面が収まり、外れた後は豆知識なし。既存の `qa-loading-cave.mjs` 8項目（洞窟の歩行・見回し・タッチ操作・失敗時を含む）・`qa-warp-menu.mjs` 6項目・`qa-contributors-cave.mjs` 6パターンも合格。全体1,478件中1,474件合格・失敗0・条件付き4件未実行、`npm run check` 合格（別のセッションが同時に進めている変更を含む作業ツリーで実行）。

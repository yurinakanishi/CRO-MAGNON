# 当たり判定の外形を配信中のGLBから測り直し（2026-10-12）

`shared/model-bounds.mts`（`MODEL_BOUNDS`）は、木・岩・テント・干し台・焚き火・木材と石の山・橋などの不可視の当たり判定（`shared/collision.mts` の `staticObstacles()`／`modelBox()`、サーバーとクライアントの体の衝突、カメラの箱の掃引 `CollisionWorld.cameraDistance`）の元になる。生成スクリプト `scripts/measure-collision-bounds.mjs` は `public/models/<key>/model.glb` を測る形のままで、ゲームが配信する各 `asset.json` の `url` と記録のSHA-256が全キーで一致していなかった。ユーザー指定により、(1) 配信GLBを測って比較、(2) 生成スクリプトを `asset.json` の `url` を測る形にして再生成し、トウヒの `trunk` をトウヒに合った測り方にする、(3) 当たり判定のテスト・既存の出現／野営地点・テントや岩の近くの経路への影響を確認、(4) SHAのずれを検出するテストを追加した。可視モデル・GLB・`asset.json` は変更していない。

## 1. 測定結果：ずれの原因と中身

`MODEL_BOUNDS` は9キー（生成スクリプトのキー一覧にない `firewood-log` を含む）。旧SHAは9件とも、2026-10-07に作り直し候補2を採用したとき（`scripts/remake/adopt_world_asset.mjs`）に測った圧縮前の正本 `model-c2.glb` のもので、C1の `model.glb` ではなかった。2026-10-09〜10の配信用軽量化（各 `asset.json` の `runtimeOptimization`）で配信が `model-c2.opt-*.glb` に替わったが、`MODEL_BOUNDS` は再生成されていない。生成スクリプトをそのまま実行すると、C1の `model.glb` を測り、`firewood-log` の項目を消して木材の山（`shared/wood-pile-layout.mts`）が壊れる状態だった。

- 配信用変換（`scripts/delivery/cook-glb.mjs`）が位置を変えるのは最大0.1mmまで。正本の測定値はそのまま使える。

## 2. トウヒの幹（`trunk`）

体はトウヒの樹冠ではなく幹とだけ衝突する（`modelBox` が `trunk` の水平の箱を使い、カメラは木を通り抜ける）。配信トウヒの表面を水平に切った外形（三角形を高さで切断した正確な値、モデル座標）：

| 高さ | 外形 x × z | |
| --- | --- | --- |
| 0.02 m | 1.01 × 1.01 m | 地面を這う根張り（軸から最大0.75m） |
| 0.10 m | 0.84 × 0.99 m | 根張り |
| 0.20 m | 0.68 × 0.77 m | |
| 0.30 m | 0.62 × 0.66 m | |
| 0.50 m | 0.53 × 0.55 m | 根張りの上端 |
| 1.00 m | 0.48 × 0.51 m | 幹 |
| 1.50 m | 0.44 × 0.48 m | 幹 |
| 2.00 m | 0.43 × 0.42 m | 幹 |
| 2.05 m | 1.06 × 1.66 m | 樹冠の始まり（2.02m） |

旧方式は「高さ0.1〜1.0mにある頂点の箱」で、トウヒでは0.12m付近の根張りの上の輪の34頂点だけで箱（0.69×0.78m）が決まっていた（帯の中の頂点は72個しかない）。0.1mの断面（0.84×0.99m）でも幹（0.48〜0.53m）でもなく、頂点の位置しだいの値で、簡略化し直せば±15cm程度変わりうる。

新しい測り方は `TRUNK_BAND = { low: 0.5, high: 1.8 }`：根張りより上、樹冠より下、立った体の高さまでの表面。各三角形を帯で切断するので、頂点の位置に左右されない。結果は x −0.233〜0.295、z −0.313〜0.234（0.53×0.55m、0.5mの断面）。帯が空、または1mより太い（樹冠や別の形の木に当たった）ときは生成を止める。拡大率1の箱の半幅は 0.346×0.392m → 0.264×0.273m。802本すべてで新しい箱は旧い箱の内側に収まる。

旧と同じくらいの広さ（根張りの上部まで含む）に戻したい場合は `TRUNK_BAND.low` を0.2にして再生成すれば、正確な外形0.68×0.76m（旧0.69×0.78m）になる。

## 3. 生成スクリプトとテスト

- `scripts/measure-collision-bounds.mjs`：`MEASURED_KEYS`（9キー、`MODEL_BOUNDS` の順）、`deliveredModel(key)`（`asset.json` の `url` を読み、ファイルのSHAが `asset.json` と一致しなければ停止）、`measureModelBounds(key)`（従来の箱・半径＋トウヒの帯の切断）。実行すると `shared/model-bounds.mts` をPrettier整形済みで書き出す。`geometryScene` は変更なし（他のテストとスクリプトが使用）。
- `node scripts/measure-collision-bounds.mjs` で再生成。変更は9件のSHA、`firewood-log` の max.x、トウヒの `trunk` だけ。
- `tests/model-bounds.test.mjs`（2件）：キーが `MEASURED_KEYS` と同じ、各SHAが `asset.json`・`world-assets.json`・実ファイルと一致、各項目が配信GLBの測定値と完全に一致。旧ファイルに対しては、SHAの確認も測り直しも9件すべてで失敗することを確認した。配信が替わった（`asset.json` の `url` が変わった）のに再生成していない場合や、`adopt_world_asset.mjs` が古い `trunk` を引き継いだ場合はこのテストが落ちる。

## 4. ゲームへの影響

同じビルドの中で `MODEL_BOUNDS` を旧／新に差し替えて比べた（`staticObstacles()` と `CollisionWorld`）：

- 障害物70,533個のうち変わったのはトウヒの幹802個と木材の山31個（最大0.35mm）だけで、すべて旧い箱の内側。
- 変わった障害物の周り124,128点（半径0.32m）：通れた→通れない 0、通れない→通れる 12,694。
- 出現6か所×5人、焚き火20か所のワープ、力尽きた後の復帰、描画復帰の着地点（計52）はすべて同一。マンモス2頭・敵34体の出現位置も同一。
- 経路（半径0.32m）：テント越し63・野営地の道具と焚き火越し158・岩越し300はすべて同一。トウヒ越し299は同一131、短縮107、延長61（最大+0.23m）。野営地の出現地点から60m以内の104目標では、テント・干し台・薪の山・焚き火・ベリーは同一。到達できなかったトウヒ1本へ到達可能になった。トウヒを目標にした経路は、終点（`nearestFree` が近い輪から探す点）が幹の別の側になることがあり、延長18件（最大+18.9m、(30.88, 111.81)のトウヒで新しい終点が他の障害物の裏側）、短縮26件。終点の選び方は従来どおりで、旧い終点も引き続き通れる。

# 配信用変換（delivery cooking）による容量の根本対策（2026-10-11）

ユーザー指定「スマホとかでも快適にゲームができるように容量とかパフォーマンス改善したい。小手先のてくにっくではなく、根本から。」への対応記録。実装・検証の範囲と、残る根本課題（次に決めること）を分けて書く。

## 原因：正本の形式のまま配信していた

採用済みGLB（`public/models`）は制作・検証の**正本**で、正確さを優先した形式になっている。これまではそれをほぼそのまま配信していた。

- 形状は全頂点がfloat32のまま。meshoptは「可逆・フィルターなし・量子化なし」（`scripts/optimization/README.md` の規則）で、位置・法線・UV・ウェイトの下位ビットをそのまま運んでいた。人物1体の形状だけで約3.5〜6MB。
- 地面・川・山・洞窟・城などの画像がPNG（1枚1〜2MB）。壁画10枚と石灰岩で約7.5MB。
- 静物のLODファイルが、本体と同じ画像を1枚ずつ重複して埋め込んでいた（薪は3ファイルに同じ画像3枚）。
- 仲間の一部は2048pxのPNG（1枚4〜5MB）で、画質方針の1024px上限を超えていた。

これまでの軽量化は「正本の画素・頂点を変えない」条件の中で数％〜20％を積み上げていた。形式そのものが配信に向いていないことが根本原因だった。

## 対策：正本と配信物を分ける

ゲームエンジンのasset cookingと同じく、**正本は変えずに、ビルド時に配信専用の派生ファイルを作る層**を追加した（`scripts/delivery/`）。採用・制作の仕組み（`scripts/optimization`、`assets/runtime-adoption`）とモデル制作の系統はそのまま。可視モデルの形・トポロジー・UV・骨・動作・材質の値は変えない。

| 対象 | 正本 | 配信物 | 誤差の上限（変換時に全要素を再デコードして検査） |
| --- | --- | --- | --- |
| 位置・UV・法線・接線・色・モーフ | float32、可逆 | meshopt EXPONENTIALフィルター（デコード後もfloat32・同じレイアウト） | 位置0.1mm、法線・接線は成分1/512（約0.2°）、UVは1/8192（1024pxの1/8テクセル） |
| スキンウェイト | float32 | 1/4096格子に丸め、合計を厳密に1へ | 成分あたり約0.06% |
| 動作の回転 | float32 | QUATERNIONフィルター14bit（glTF標準の正規化int16、GLTFLoaderでfloatのトラックに戻る） | 3e-4 rad |
| 動作の移動・拡大 | float32 | EXPONENTIAL | 0.1mm／1e-4 |
| インデックス・関節番号・逆バインド行列・時刻 | — | 可逆のまま（既存のmeshopt列はそのまま） | 0 |
| OPAQUE材質の色PNG | PNG | WebP q88（PSNR 36dB未満ならnear-lossless） | PSNRを記録 |
| 法線・データ用PNG | PNG | near-lossless WebP（色差サブサンプリングなし） | PSNRを記録 |
| アルファを使う画像（MASK/BLEND、実行時に透過で使う川） | PNG | PNGのまま | 0 |
| 1024pxを超える画像（仲間の2048px） | 2048 | 1024へ縮小（法線は再正規化） | 縮小後の基準に対してPSNRを記録 |
| 静物（static/tree/terrain/bridge）のLOD | 1段階1ファイル | 1ファイルの複数scene（既存のpacked levels）。同じ画像は1回だけ格納 | 全accessor・画像のバイト一致 |
| 洞窟の石灰岩（不透明） | PNG 2.2MB | WebP q90（0.45MB） | PSNR 39.0dB |
| 洞窟の壁画9枚（透過） | PNG | パレットPNG（libimagequant、PNGのまま） | 乗算済み色PSNR 40.5〜42.6dB |
| 選択画面などの肖像（固定URL） | PNG | 同じURLのパレットPNG（manifestがSHAを持つ画像は正本のまま） | PSNR 37dB以上のみ |

- 実行時の型は変えていない。頂点属性はfloat32・非インターリーブのままなので、地形のフィットや衝突計算など頂点を直接読むコードはそのまま動く（`src/source-surface-fit.ts` などを確認）。
- 配信物の名前は内容のSHAで決まる（`<元の名前>.cook-<sha16>.glb`）。同じ正本・同じレシピからは同じバイト列ができ、`dist/delivery/cache/` に保存して再ビルドでは再利用する。レシピ（コード・方針・meshoptimizer・libwebp等の版）が変われば別のキーになる。
- 公開・持ち運び・展示のビルドは、正本を従来どおり全件SHA・採用グラフで検査したあと、配信物を同梱し、manifestを配信物を指すように書き換える。ソースのmanifestは変えない。
- ローカルサーバー（3000番の通常起動）は `npm start`／`npm run dev` の起動前に `dist/delivery/overlay.json` を用意し、manifestと配信物を同じように返す（`infrastructure/node/delivery-overlay.mts`）。正本のSHAが一致するレコードだけを書き換えるので、あとで採用された素材は正本のまま返る。`CRO_DELIVERY=masters` で正本を返す（比較用）。テストや検証用サーバーは既定で正本を返す。

## 結果

### 初回の待ち時間（同じ測定ハーネス・同じ回線条件）

Windows Chrome、390×844、DPR1、下り10Mbps／上り5Mbps、遅延50ms、CPU4倍制限、空キャッシュ。同じソース（HEAD `2fda5d8`＋本変更）から作った持ち運び版2つ（正本のまま／配信物）を比較。実スマホの測定ではない。

| 指標 | 正本のまま（2回） | 配信物（2回） |
| --- | --- | --- |
| 確定→洞窟で操作可能（アプリ内） | 14.18〜14.21秒 | **6.50〜6.58秒** |
| 確定→通常世界の操作有効化（アプリ内） | 34.97〜35.44秒 | **19.73〜19.99秒** |
| 確定タップ→実タッチ移動の確認（QA観測） | 38.28〜38.46秒 | **23.11〜23.36秒** |
| 操作可能までの受信本文 | 37.08MB | **18.02〜18.81MB** |
| ページ表示→人物選択 | 5.77〜5.87秒 | 5.84〜5.86秒（変化なし） |

### 配信物の総量

| | 正本 | 配信物 |
| --- | --- | --- |
| 公開MMO版のGLB（101レコード） | 125.9MiB | 68.4MiB（81ファイル） |
| 公開MMO版の全静的ファイル（同じソースで比較） | 178.6MiB（576ファイル） | 115.8MiB（556ファイル） |
| 持ち運び版の全体 | 392.2MiB | 266.1MiB |
| 洞窟の画像10枚 | 7.51MB | 1.97MB |

公開MMO版では全GLBが内容のSHAで名付けられるため、`_headers` の1年immutableキャッシュが有効になった（正本のままでは仲間の旧名ファイルがあり無効）。再訪時はGLBを再取得しない。

### 見た目の検証

- 変換した128ファイルを実Chrome（ANGLE D3D11）で正本と並べて描画。シーン・ノード・頂点数・インデックス数・属性・材質・動作の構造は全件一致。4方向の画像のPSNRは最低35.4dB（2048→1024へ縮小した仲間）、ほかは36dB以上で大半は45dB以上。全動作×5時点の骨変形後の頂点位置の差は最大1.14mm（体高3.6mのマンモスの草を食む動作）、人物は0.36mm以下。証拠 `output/delivery-qa/final-r01/`。
- 洞窟内の同じ視点3枚で、壁画・石灰岩・松明の照明を正本と比較して差は判別できない（`output/playwright/delivery-r01/cave-sheet.png`、拡大 `cave-zoom.png`）。
- **見える差がある箇所：** 2048pxから1024pxへ縮小した仲間（sagasa等）は、靴の縞など小さなUV領域の細部が近距離でやや柔らかくなる（`output/delivery-qa/sheet-r03-shoe.png`）。画質方針の1024px上限に合わせた結果で、GPUメモリーは1枚あたり約22MB→5.6MB。戻す場合は `DEFAULT_POLICY.maxTextureEdge` を2048にする。
- 実パッケージ（持ち運び版のNodeサーバー、公開MMO版の隔離Miniflare Worker）で開始→洞窟→通常世界→実タッチ移動・停止が成功し、正本GLBの要求0・配信物の要求を確認（`output/playwright/delivery-r01/packages-final-r01/`）。

### 変わっていないもの（正直な範囲）

- **描画性能は変わらない。** 形式の変更なので、三角形数（キャンプ約70万、遠景約86万）、描画呼び出し（45〜118）、30fps・p95 33〜42ms、GPUテクスチャ容量（315〜397MB）は同条件で変更前と同じ（`perf-baseline-r01`／`perf-r03-r01`、`tex-*`）。
- 5秒・必須4MBの目標は未達。通常世界まで約20秒、うち洞窟→通常世界の約13秒は周辺15テンプレートの約9MBの受信と、到着前の地形準備（CPU4倍で約4秒）。
- 実Android／iPhone、実回線、発熱・電池は未検証。

## 残る根本課題（次に決めること）

1. **人物の頭部（最大の残り）。** 顔を作り直した3体の頭部は5万〜6万三角形で、位置で見ると1.7万〜2.5万本の開いた辺がある継ぎはぎのメッシュ。属性・継ぎ目を守る簡略化では8〜30％しか減らない（試算済み）。他の人物の頭部は約1.35万三角形。リメッシュ＋テクスチャの再ベイクで頭部を約1.3万三角形にすると、人物3体が7.3万→約3.3万、6.9万→約3.1万、9.9万→約5.3万三角形になり、キャンプの描画三角形の約4割を占める人物の負荷と人物の転送量が大きく減る。顔の品質を伴う制作作業なので、別revisionとして顔の近接比較を行い、ユーザーの確認を得てから採用する。数値は `output/delivery-r01-tests/character-topology.txt`。
2. **GPUテクスチャ315〜397MB。** 1024px RGBAが約56枚分。人物・小物の法線マップを512pxにする、法線マップだけUASTC（KTX2）を試すなど、外観と転送量を合わせて評価する。
3. **起動JavaScript 6.83MB（gzip約1.1MB）。** 地形・海岸・衝突の数値データがJSに埋め込まれており、人物選択まで約5.8秒のうち解析・評価の時間が大きい。バイナリにして必要時に読む。
4. **通常世界へ入る条件。** 現在は半径82m以内の全テンプレートを待つ。洞窟を歩く間に読み終わる設計は保ち、入場条件を見える近景に絞るかは方針の判断。

## 使い方

```sh
npm run cook                                   # 型ビルド → 配信物の用意（ローカルサーバー用 overlay）
node scripts/delivery/cook-report.mjs public/models/x/model.glb   # 1ファイルの変換結果と誤差を表示
node scripts/delivery/qa-cooked-models.mjs --out output/delivery-qa/<run> [model-key ...]
npm run build:cloudflare                       # 公開版（配信物を同梱）
CRO_DELIVERY=masters npm start                 # 比較用に正本を返す
```

テスト：`tests/delivery-cook.test.mjs`（変換・誤差・画像・LODまとめ・キャッシュ・manifest書き換え）、`tests/delivery-overlay.test.mjs`（ローカルサーバー）。全体1,442件中1,438件合格・失敗0・条件付き4件未実行（Pillow 2件・任意ベンチ2件）。`npm run check`（型・strict・602 JS構文・依存境界）、変更したTypeScriptの書式も合格。

既存の3000／8787／4173の停止・再起動、ユーザー保存の編集、公開デプロイ、commit／pushは行っていない。測定用のパッケージ・ログは `output/delivery-r0*-*`、`output/playwright/delivery-r01/`、`output/delivery-qa/`。
